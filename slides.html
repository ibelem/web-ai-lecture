为什么要在本地跑

云端 vs 本地：三个维度的取舍

维度云端 API浏览器本地推理
成本按 token 计费，量大很贵零边际成本
隐私数据上传到第三方服务器数据不出本地
延迟每次都要网络往返本地直算，无网络
离线断网即不可用缓存后可离线
模型规模可跑超大模型受本地内存/算力限制
知识时效易接入最新数据取决于本地模型

不是谁取代谁 —— 而是该本地的本地，该云端的云端。

为什么要折腾本地推理？四个理由它赢，两个理由它输，看这张表。 成本：云端按 token 收费，一个班 50 个学生天天调，账单很快上来。本地是零边际成本，电费而已。 隐私：这是最硬的理由。医疗、法律、个人笔记这类数据，你愿意传给第三方吗？本地推理数据根本不出这台机器。 延迟：云端每次请求都要网络往返，本地是直接算，省掉这一跳。 离线：飞机上、地铁里、内网环境，云端直接歇菜，本地照跑。 但要诚实 —— 本地也有输的地方：跑不了几百 B 的超大模型，本地内存装不下；知识时效也受限于你下载的那个模型。 所以结论不是"本地取代云端"，而是工程师要有判断力：该本地的本地，该云端的云端。这句话这堂课会反复出现。

现在讲硬件。AI PC 和普通电脑差在哪？答案就在这三个方块。 CPU，通用计算，什么都能干，但跑 AI 这种海量并行计算，它慢，因为核心数太少。 GPU，几千个小核同时算，特别适合矩阵乘法，是跑大模型的主力。游戏显卡能跑 AI 就是这个原因。 重点是第三个：NPU，神经网络处理单元。这是这一代 AI PC 的标志。它专门为神经网络的固定计算模式设计，最大的优点是能效 —— 同样跑一个 AI 任务，NPU 的功耗远低于 GPU，风扇都不用转，笔记本续航友好。 记住这个分工：GPU 强在峰值算力，NPU 强在能效。后面你会看到 WebGPU 对应 GPU，WebNN 重点对应 NPU。

模块一 · 10–25 min

WebGPU
浏览器的通用算力

让网页摸到 GPU 的几千个核心

第一个模块，WebGPU。一句话定位：它是浏览器摸到 GPU 通用算力的那把钥匙。 这一节的目标不是教你写 GPU 代码，而是让你理解：为什么跑大模型需要它，它和老的 WebGL 差在哪。
问题先行

痛点：浏览器原来摸不到 GPU 算力

浏览器是个沙箱

为了安全，网页不能直接碰底层硬件。想用 GPU 做计算？没有正经的口子。

老办法：WebGL 凑合

WebGL 是为画 3D 图形设计的。想用它做通用计算，得把数据伪装成"纹理和像素"，绕一大圈，又难又慢。

结果

在 WebGPU 之前，浏览器里跑 AI 基本靠 CPU（WASM），慢到没法用大模型。

GPU 明明就在那，网页却用不上 —— 这就是 WebGPU 要解决的问题。

讲新技术，我习惯先讲它解决什么痛点，否则你记不住。 浏览器是个沙箱，为了安全，网页不能随便碰你的硬件 —— 想想看，如果任何网页都能直接操控你的 GPU 和内存，那太危险了。所以历史上，网页想用 GPU 算力，没有正经口子。 那 WebGL 呢？WebGL 确实能用 GPU，但它是为画 3D 图形设计的，比如游戏、地图。你想用它做 AI 计算，得把矩阵数据伪装成图片纹理，把计算伪装成"渲染像素"，绕一大圈，代码难写，性能也打折。 所以 WebGPU 出现之前，浏览器里跑 AI 基本只能靠 CPU，也就是 WASM，慢得跑不动大模型。GPU 明明就躺在你电脑里，网页却够不着。这就是 WebGPU 要解决的核心问题。
WebGPU 是什么

现代 GPU 接口，原生支持通用计算

  • 定位：W3C 标准，浏览器里的下一代 GPU API，取代 WebGL。
  • 底层：直接映射到原生的 Vulkan / Metal / Direct3D 12，性能接近原生。
  • 关键能力：原生支持 Compute Shader（计算着色器） —— 不用再伪装成画图，可以直接写"通用并行计算"。
  • 对 AI 的意义：矩阵乘法、张量运算这些 AI 的核心操作，终于能在浏览器里高效跑在 GPU 上。

一句话：WebGPU 让网页第一次能正经地把 GPU 当成计算器用，而不只是画图工具。

那 WebGPU 是什么？它是 W3C 的标准，浏览器里的下一代 GPU 接口，定位就是取代 WebGL。 它底层直接对接操作系统的原生图形 API —— Windows 上是 Direct3D 12，Mac 上是 Metal，Linux/安卓上是 Vulkan。所以它性能接近原生，不是玩具。 最关键的一点：它原生支持 Compute Shader，计算着色器。这个词你不用记，记住它的意义：你终于可以直接写"通用并行计算"，而不用像 WebGL 那样伪装成画图。 对 AI 来说，这就是解放。AI 的核心运算是什么？矩阵乘法、张量运算。这些现在能高效地跑在 GPU 上了。 一句话总结：WebGPU 让网页第一次能把 GPU 当成一台正经的计算器，而不只是画图工具。

建立直觉 · 不写代码

为什么 GPU 适合 AI：并行的力量

CPU 的算法

几个大力士，一个接一个搬箱子。

核心少（几个~几十个），但每个很强、很灵活。适合复杂、有先后顺序的任务。

GPU 的算法

几千个小工，同时各搬一个箱子。

核心极多（几千个），每个简单，但一起上。适合"同一种运算重复几百万次"。

大模型在算什么？本质是海量的矩阵乘法 —— 同一种运算重复几百万次。
这正是 GPU 的主场。这就是为什么 LLM 要用 WebGPU。

不写代码，给你一个直觉，理解为什么 GPU 适合 AI。 想象搬一仓库的箱子。CPU 的方式是：雇几个大力士，一个接一个搬。每个人很强、很聪明，能处理复杂情况，但人少，量大就慢。 GPU 的方式是：雇几千个小工，每人同时搬一个箱子。每个小工很弱、只会干简单活，但人多，一起上，瞬间搬完。 关键在于任务的性质。如果任务是"同一种简单操作，重复几百万次"，那 GPU 这种打法碾压 CPU。 大模型在算什么？剥开看，本质就是海量的矩阵乘法 —— 把输入和权重矩阵相乘，同一种运算重复几百万次。这正是 GPU 的主场。 所以这句话你要记住：LLM 用 WebGPU，是因为它要做海量并行的矩阵乘，而 GPU 天生为此而生。

模块二 · 25–40 min

WebNN API
直达 CPU / GPU / NPU

浏览器里唯一能摸到 NPU 的神经网络专用标准

第二个模块，WebNN。如果说 WebGPU 是通用算力的钥匙，那 WebNN 是神经网络专用加速的钥匙，而且是目前 Web 端唯一能摸到 NPU 的标准。 这一节我会讲清楚：它和 WebGPU 到底分工有什么不同，以及为什么 Intel AI PC 的 NPU 这么重要。
问题先行

痛点：通用算力不够省电

WebGPU 很强，但…

用 GPU 跑 AI，算力够，可是功耗高、发热大。笔记本上跑一会儿风扇狂转、电量哗哗掉。

而且要自己组织计算

WebGPU 是通用工具，怎么把神经网络拆成高效的并行计算，得开发者/库自己操心。

能不能更聪明？

神经网络的计算其实很有规律（卷积、矩阵乘、激活…）。
如果有一块专门为这些运算设计的硬件（NPU），再有一个标准直接把任务交给它 —— 又快又省电。

这就是 WebNN。

同样先讲痛点。WebGPU 已经很强了，为什么还要 WebNN？ 因为 GPU 跑 AI，算力够，但有代价：功耗高、发热大。你笔记本用 GPU 跑模型，跑一会儿风扇就狂转，电量哗哗往下掉。对移动设备这是大问题。 另一个问题：WebGPU 是通用工具，它不知道你在跑神经网络。怎么把一个神经网络拆成高效的 GPU 计算，得开发者或者库自己操心，很复杂。 那能不能更聪明点？神经网络的计算其实特别有规律 —— 来来去去就是卷积、矩阵乘、激活函数这几样。如果我造一块硬件，专门为这几样运算优化，再提供一个标准，让你能把整个网络直接"交给"这块硬件去跑，那不就又快又省电吗？ 这块专用硬件就是 NPU，这个标准就是 WebNN。
WebNN 是什么

把神经网络交给系统去加速

  • 定位：W3C 正在标准化的神经网络专用 Web API。
  • 思路：你描述一张计算图（用了哪些算子），WebNN 把它交给操作系统的 ML 加速栈，由硬件决定怎么跑最优。
  • 能摸到的硬件：CPU、GPU，以及关键的 NPU —— 这是 Web 端目前唯一直达 NPU 的标准。
  • 和 WebGPU 的区别：WebGPU 给你"算力"，你自己组织；WebNN 给你"加速服务"，你只描述网络。

类比：WebGPU 是租一间厨房自己做菜；WebNN 是点一道菜，后厨怎么高效做是它的事。

WebNN 是什么？W3C 正在标准化的、神经网络专用的 Web API。 它的思路和 WebGPU 很不一样。WebGPU 是给你算力，你自己写怎么算。WebNN 是：你只要描述一张计算图 —— 我这个网络用了卷积、用了矩阵乘、用了哪些激活 —— 然后把这张图交给操作系统的 ML 加速栈，剩下的事，"怎么在硬件上跑得最优"，由系统和硬件去决定。 它能摸到 CPU、GPU，以及最关键的 NPU。划重点：WebNN 是目前 Web 端唯一能直达 NPU 的标准。WebGPU 摸不到 NPU。 一个类比：WebGPU 像租一间厨房，锅碗瓢盆给你，菜你自己做。WebNN 像去餐厅点一道菜，你只说要什么，后厨怎么高效做出来是它的事。对开发者来说，WebNN 更省心，对硬件来说，它能做更激进的优化。
构图思路 · 看个意思

MLGraphBuilder：把网络搭出来

// 1. 拿到一个加速上下文（可指定偏好 NPU）
const context = await navigator.ml.createContext({ deviceType: 'npu' });
const builder = new MLGraphBuilder(context);

// 2. 用算子搭计算图：输入 → 卷积 → 激活
const input  = builder.input('x', { dataType: 'float32', shape: [1,3,224,224] });
const conv   = builder.conv2d(input, weights);
const output = builder.relu(conv);

// 3. 编译成图，交给硬件执行
const graph = await builder.build({ output });

实际开发你几乎不会手写这个 —— ONNX Runtime Web / Transformers.js 会帮你生成。看懂"描述图、交给硬件"这个思路即可。

给你看一眼 WebNN 的代码长什么样，建立印象就行，不用记。 第一步，拿一个加速上下文，注意这里可以指定 deviceType 是 'npu'，明确告诉系统我想用 NPU。 第二步，用 builder 一个算子一个算子把网络搭出来：定义输入，接一个卷积 conv2d，再接一个激活 relu。你看，这就是在"描述一张图"，描述这个网络由哪些运算组成。 第三步，build，把这张图编译好，交给硬件执行。 但我要强调：实际开发你几乎永远不会手写这段代码。太底层了。真实场景里，ONNX Runtime Web 或者 Transformers.js 会自动帮你生成这些。我给你看，只是让你理解 WebNN 的工作方式 —— 描述图、交给硬件。这个思路记住就够了。

模块三 · 40–55 min

ONNX Runtime Web
统一推理引擎

一个模型，三种 backend，换一行就换硬件

第三个模块，ONNX Runtime Web，简称 ORT Web。 前面两个模块是底层的桥梁，比较硬核。从这里开始往上走，越来越接近你平时写的代码。ORT Web 是中间这层引擎，它的核心价值就一句话：一个模型，三种后端，换一行配置就能换硬件。
先搞懂 ONNX

ONNX：模型的通用格式

问题

模型在 PyTorch 训练、在 TensorFlow 训练… 格式各不相同，换个地方部署就头疼。

ONNX 的方案

一个开放的中间格式。各框架训练完都能导出成 .onnx，到处都能加载运行。

类比

ONNX 就像 AI 模型界的 PDF。

不管你用什么软件写的，导成 PDF，谁都能打开。模型导成 ONNX，哪儿都能跑。

先搞懂 ONNX 是什么，这是 ORT Web 的基础。 问题是这样的：模型有的人用 PyTorch 训练，有的人用 TensorFlow，还有别的框架，各家保存格式都不一样。你训练好一个模型想拿到别处部署，格式不兼容，很麻烦。 ONNX 的方案：定一个开放的中间格式。不管你用什么框架训练，训练完都能导出成一个 .onnx 文件，然后这个文件在任何支持 ONNX 的地方都能加载运行。 最好记的类比：ONNX 就是 AI 模型界的 PDF。你用 Word、用 Pages、用什么都行，导成 PDF，对方不管什么设备都能打开。模型导成 ONNX，也是哪儿都能跑 —— 包括我们今天的主角，浏览器。
它在哪一层

ORT Web 是承上启下的那一层

上面只管"要跑模型"，下面是"三种硬件后端"。ORT Web 负责把上面的请求落到下面某个后端。

ORT Web 在我们那张大图里处于承上启下的位置，这页讲清楚它两头连着谁。 上面：是你的代码，或者更常见的，是 Transformers.js。它们说"我要跑这个 ONNX 模型"。 ORT Web 在中间：它负责把模型文件加载进来，选一个后端，然后调度执行。 下面：是三种 Execution Provider，执行后端 —— WASM 用 CPU，WebGPU 用 GPU，WebNN 用 NPU/GPU。这就是前两个模块讲的东西，现在它们以"后端选项"的身份出现了。 所以 ORT Web 干的事很清楚：上面只管说要跑什么模型，下面有三种硬件后端，ORT Web 负责把请求落到你选的那个后端上。它是个调度员、翻译官。
核心取舍

三种 Execution Provider 怎么选

Backend跑在优点取舍适合
WASMCPU兼容性最好，处处能跑最慢兜底 / 小模型
WebGPUGPU并行强，吞吐高需 GPU 支持大模型 / LLM
WebNNNPU/GPU/CPU能效高、省电较新，算子在扩CNN 视觉 / 常驻推理

选择策略：能 WebGPU / WebNN 就用，自动回退 WASM 兜底。一份代码，最优体验 + 永不崩。

这三个后端怎么选，是工程上的核心取舍，看这张表。 WASM，跑在 CPU 上。优点是兼容性无敌，任何浏览器、任何设备都能跑。缺点是慢。定位是兜底，或者跑很小的模型。 WebGPU，跑在 GPU 上。并行能力强，吞吐高。缺点是需要 GPU 和 WebGPU 支持。适合大模型，尤其是 LLM。 WebNN，跑在 NPU/GPU/CPU 上。优点是能效高、省电。缺点是比较新，算子还在扩展。适合 CNN 视觉任务和需要常驻的推理。 实战里的选择策略很简单：优先用 WebGPU 或 WebNN，如果环境不支持，自动回退到 WASM 兜底。这样一份代码，在好的设备上跑出最优体验，在差的设备上也永远不崩。这是 ORT Web 帮你省心的地方。
看一段真代码

ORT Web 最小推理：四步

// 1. 引入 ONNX Runtime Web
import * as ort from 'onnxruntime-web';

// 2. 创建推理会话 —— 这里选后端！优先 WebGPU，回退 WASM
const session = await ort.InferenceSession.create('model.onnx', {
  executionProviders: ['webgpu', 'wasm']
});

// 3. 准备输入张量
const input = new ort.Tensor('float32', data, [1, 3, 224, 224]);

// 4. 跑！
const results = await session.run({ x: input });

换硬件？只改第 2 步的 executionProviders —— 比如换成 ['webnn','wasm']。其余一字不动。

看一段真实代码，体会 ORT Web 多简洁。四步。 第一步，引入 onnxruntime-web 这个库。 第二步，创建推理会话，传入模型文件。注意这一行最关键 —— executionProviders 这个数组，就是在这里选后端！我写的是先试 webgpu，不行就回退 wasm。这个数组就是前面讲的"优先用好的，回退兜底"策略的代码体现。 第三步，准备输入。AI 模型的输入是张量 Tensor，这里是一个 1×3×224×224 的图像张量，就是一张 224×224 的彩色图。 第四步，run，跑起来，拿结果。 最想让你记住的一点：如果我想从 GPU 换到 NPU，我只需要改第二步那一行，把 'webgpu' 换成 'webnn'，其他代码一字不动。这就是"换一行就换硬件"的真正含义。模型不用改、输入输出不用改，只换后端。
本模块的核心收获

同一个 ONNX 模型，
改一行 executionProviders，
就能在 CPU / GPU / NPU 之间切换。

ORT Web 把"用什么硬件"变成了一个配置项，而不是一次重写。

这页是 ORT Web 模块的核心收获，我让它单独占一屏，因为太重要。 同一个 ONNX 模型，改一行 executionProviders 配置，就能在 CPU、GPU、NPU 之间自由切换。 想想这件事的意义：在没有 ORT Web 之前，你想从用 CPU 改成用 GPU，可能要换整套代码、换库、甚至换模型格式。现在，硬件选择变成了一个配置项，一个字符串数组。 这就是抽象的力量。ORT Web 把"用什么硬件"这个原本很重的决定，变轻了，变成了一个可以随时调的开关。待会儿动手环节，你们就会亲手切换这个开关，对比不同后端的速度。

Transformers.js
一行代码用 Hugging Face

把整套技术栈，收敛成一个 pipeline()

第四个模块，Transformers.js，我们终于爬到栈的最顶层了。 前面三层 —— WebGPU、WebNN、ORT Web —— 听起来都还有点门槛。Transformers.js 的使命就是把这一切包起来，让你用一行代码就能跑模型。这是离学生最近、最容易上手的一层。
Transformers.js 是什么

Hugging Face 官方的 JS 版

背景

Hugging Face 是全球最大的开源模型社区。Python 的 transformers 库是 AI 圈的"标配"。

Transformers.js

官方出的 JavaScript 版，API 几乎和 Python 一样，直接在浏览器跑，底层用 ORT Web。

# Python（服务器）
from transformers import pipeline
pipe = pipeline('sentiment-analysis')
pipe('I love this!')

// JavaScript（浏览器）
import { pipeline } from '@huggingface/transformers';
const pipe = await pipeline('sentiment-analysis');
await pipe('I love this!');

会 Python transformers 的人，几乎零成本迁到浏览器。

Transformers.js 是什么？Hugging Face 官方出的 JavaScript 版。 先说背景：Hugging Face 是全球最大的开源 AI 模型社区，你想要的模型基本都能在上面找到。它的 Python 库叫 transformers，是 AI 圈的标配工具，几乎人人在用。 Transformers.js 就是这个库的官方 JS 版本。妙就妙在：它的 API 设计得和 Python 版几乎一模一样，但它直接在浏览器里跑，底层用的就是我们刚讲的 ONNX Runtime Web。 看右边两段代码对比，Python 和 JavaScript，几乎长得一样 —— 都是 import pipeline，都是 pipeline('sentiment-analysis')，然后调用。 这意味着什么？一个会用 Python transformers 的算法工程师，几乎零学习成本就能把模型搬到浏览器里。这个设计非常聪明，直接复用了整个社区的肌肉记忆。
核心抽象

pipeline(task, model, options)

const generator = await pipeline(
  'text-generation',                       // ① 任务类型
  'HuggingFaceTB/SmolLM2-360M-Instruct',    // ② 模型名（自动从 Hub 下载）
  { device: 'webgpu' }                       // ③ 选项：用哪个硬件后端
);

const out = await generator('你好，介绍一下你自己');
  • ① 任务：text-generation / image-classification / translation…
  • ② 模型：填 Hugging Face 上的名字，库自动下载 + 缓存。
  • ③ 选项：device: 'webgpu' | 'wasm' —— 又是这一行决定用什么硬件。
Transformers.js 的核心就是这一个函数：pipeline，三个参数。 第一个参数，任务类型。你要干嘛？文本生成填 text-generation，图像分类填 image-classification，翻译填 translation。Transformers.js 支持几十种任务。 第二个参数，模型名字。直接填 Hugging Face 网站上那个模型的名字，库会自动帮你从 Hub 下载，并且缓存起来。这里我填的是 SmolLM2，一个很小的语言模型。 第三个参数，选项。注意 device 这一行 —— 又是它！'webgpu' 还是 'wasm'，决定用什么硬件。你看，从 ORT Web 的 executionProviders，到这里的 device，"选硬件"这个动作一路传上来，始终是一行配置。 拿到 generator 之后，直接像调函数一样把输入喂进去，就出结果了。三个参数定义一个 AI 能力，一行调用拿到结果。这就是为什么说 Transformers.js 把整套技术栈收敛成了一个 pipeline。

现在把今天讲的四个模块，用一次真实的调用串起来，这是那张大图的第二次出现。 你写的，只有最上面这一行：pipeline，文本生成，某个模型，device 设成 webgpu。就这一行。 接下来全自动：Transformers.js 解析你要做文本生成，去 Hub 把模型下载下来，转成 ONNX 交给 ORT Web。 ORT Web 加载这个 .onnx 模型，看到你 device 写的是 webgpu，就选 WebGPU 这个后端。 WebGPU 把计算桥接到 GPU。如果你写的是 webnn，这里就换成 WebNN，桥接到 NPU。 最后，AI PC 的 GPU 或 NPU 真正执行计算，结果一路返回到你那一行代码。 看到没？你只写了第一行，下面三层全自动。这就是抽象层层叠加的威力 —— 每一层都把下面的复杂度藏起来，最后用户只面对一个 pipeline。但今天你理解了底下每一层在干嘛，这就是这堂课和"只会调 API"的区别。

模型下载到本地后，推理时数据不再出网。你的输入永远留在这台机器。

讲一下模型的生命周期，这解释了开场那个"拔网线还能跑"的魔术。 首次运行：Transformers.js 从 Hugging Face Hub 把模型权重下载下来，可能几十 MB 到几百 MB，然后存进浏览器的 Cache Storage —— 这是浏览器专门用来缓存大文件的地方。 再次运行：直接从缓存读，秒开，不再重新下载。所以第一次慢，之后都快。 断网之后：模型已经在本地缓存里了，所以完全离线可用。这就是开场我拔掉 WiFi 还能继续生成的原因 —— 模型早下好了，根本不需要网。 最后强调隐私含义：模型下载到本地之后，你每次推理，输入数据是在本地算的，不再出网。你打的字、你上传的图，永远留在这台机器上。对隐私敏感的应用，这是杀手级特性。回扣开头那张"云端vs本地"的表，这就是"数据不出本地"的技术实现。

别以为 Web AI 只能做聊天机器人。Transformers.js 支持的任务非常广，看这四类。 文本：生成、情感分析、翻译、摘要、问答、分类，传统 NLP 能干的基本都有。 视觉：图像分类、目标检测、图像分割、背景移除、深度估计。背景移除特别实用，做个网页版抠图工具，完全本地，不用上传照片。 音频：语音识别（把语音转文字）、语音合成、音频分类。本地字幕、本地语音助手都能做。 多模态：图文检索、给图片生成描述、视觉问答、文本嵌入（做语义搜索的基础）。 关键是，做这么多事，你用的还是同一套 pipeline()，只是换个任务名、换个模型名。而且全在浏览器里、全本地。这给你们的课后作业留了巨大空间 —— 后面会让你们自己挑一个做。

轨道 A · 操作步骤

🅰 WebGPU 跑大语言模型

  1. 双击打开 track-a-webgpu-llm/index.html
  2. device 选 webgpu，点「加载模型」（首次下载等待）
  3. 输入问题，点「生成」，看流式输出
  4. 记下 首 token 延迟 和 tok/s
  5. 切 device 为 wasm 重新加载，对比速度
const gen = await pipeline(
  'text-generation',
  '…/SmolLM2-360M-Instruct',
  { device: 'webgpu' }   // ← 这里切硬件
);
const out = await gen(messages, {
  max_new_tokens: 128, streamer
});

核心就这一段。页面已封装好，你专注体验和对比。

轨道 A 的操作步骤，跟着做。 第一步，双击打开 track-a 那个 html 文件。它直接在浏览器里开，不需要服务器。 第二步，device 默认就是 webgpu，点"加载模型"。第一次会下载模型，几十 MB，等进度条走完。这里可以让学生互相帮忙，网络慢的同学耐心等。 第三步，在输入框打个问题，点"生成"，你会看到文字一个个蹦出来，流式输出。 第四步，记下两个数字：首 token 延迟，就是你点生成到第一个字出现花了多久；还有 tok/s，每秒生成多少 token。 第五步，关键对比：把 device 切成 wasm，重新加载模型，再生成一次。对比 tok/s。你会明显看到 WebGPU 比 WASM 快很多 —— 这就是 GPU 算力的直观体现。 右边是核心代码，其实就是我们讲过的 pipeline，页面已经封装好了，你不用写代码，专注体验和对比这两个后端的差异。 【巡场】这五分钟我会下去转，帮大家解决加载问题。常见问题：网络慢、或者旧浏览器不支持 WebGPU —— 后者就先用 wasm 体验流程。

③ 断网再生成

关掉 WiFi 再点生成，依然能跑 —— 模型已缓存，全程本地、零联网、零成本。

做完轨道 A，停下来想三件事，这是把体验上升成认知的关键。 第一，WebGPU 比 WASM 快多少？看你记的 tok/s。这个差距，就是把计算从 CPU 挪到 GPU 的纯收益，你亲手量出来的。 第二，打开任务管理器，切到性能页看 GPU。生成的时候 GPU 占用会飙升。这是证据 —— 证明计算真的发生在你这台笔记本的 GPU 上，不是我骗你偷偷调云端。 第三，再玩一次断网那个魔术：关 WiFi，点生成，照跑。这时候你应该已经理解为什么了 —— 模型缓存在浏览器里，全程本地，不联网，零成本。 这三点把"我跑了个 Demo"变成"我理解了本地推理的价值"。

🅱 WebNN 跑图像分类

判断力 · 工程师最值钱的部分

本地 Web AI：能做什么，别勉强什么

✅ 适合本地

  • 中小模型（几亿参数级）
  • 隐私敏感数据（照片、笔记、录音）
  • 离线 / 弱网场景
  • 高频常驻推理（摄像头、字幕）
  • 想省云端成本的高频调用

⚠ 仍需云端

  • 超大模型（几百 B，本地装不下）
  • 需要最新知识 / 实时数据
  • 需要跨设备同步的重计算
  • 对首次加载体积极敏感的场景

该本地的本地，该云端的云端 —— 还记得开头这句吗？

最后讲判断力，这是工程师最值钱的部分，比会用任何工具都重要。 什么适合放本地？中小模型，几亿参数级别的，本地能装下、能跑动。隐私敏感的数据 —— 照片、笔记、录音，本地处理最安心。离线或弱网场景。高频常驻的推理，比如摄像头、实时字幕。还有，想省云端成本的高频调用 —— 量大的时候本地的零成本很香。 什么还得用云端？超大模型，几百 B 参数那种，本地内存根本装不下。需要最新知识或实时数据的，本地模型是"冻结"在训练那一刻的。需要跨设备同步的重计算。还有对首次加载体积特别敏感的场景 —— 毕竟本地要先下载几十上百 MB 的模型。 记得开头那句话吗？该本地的本地，该云端的云端。绕了一圈，现在你应该真正理解这句话的分量了。技术选型不是追新，是匹配场景。
